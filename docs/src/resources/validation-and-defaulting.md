# Validation and Defaulting

Kaalm runs no admission webhook server, validating or mutating (the conversion webhook the controller serves since v0.6.0 translates between API versions and enforces nothing; see [API Versioning and Deprecation](../operations/api-versioning.md)). Every rule on this page is enforced either by CEL expressions (`x-kubernetes-validations`) embedded in the CRD OpenAPI schema, which the API server evaluates at apply time, or by the relevant reconciler at reconcile time. This keeps the control plane free of a webhook availability dependency, and it lets rules that span resources surface violations on pre-existing objects as recoverable status rather than blocked writes.

## Cross-Resource Validation

The constraints below are enforced through a mix of the two mechanisms:

- **CRD CEL** (`x-kubernetes-validations`): checked at apply time, rejected by the apiserver before the object is stored.
- **Reconcile-time checks**: performed by the relevant reconciler; violations surface in status.

Most reconcile-time violations set `Ready=False` with a specific `reason`. AgentClass-vs-Agent-spec mismatches (rules 2, 5, 24, 26, and 30, joined since v0.4.0 by the tool-plane rules 35 to 38) follow the established class-mismatch handling instead: the Agent transitions to `phase=Degraded` with `reason` set per the rule (`ClassConstraintViolation` for image, provider, or tool-provider mismatches, `PersistenceNotAllowed` for persistence, `HibernationNotAllowed` for hibernation, `HandlerMountNotAllowed` for handler mounts, `ToolNotInCatalog` for rule 38's catalog misses). For the rules of that family that also apply to AgentTask (2, 5, 24, and 35 to 38), the AgentTask transitions to `phase=Failed` instead, because AgentTask has no `Degraded` phase; rules 26 and 30 are Agent-only, since hibernation and handler mounts do not apply to one-shot tasks. Rule 29, a spec-internal hibernation/persistence coupling, reuses the same `Degraded` handling with `reason=HibernationRequiresPersistence`. A small subset (rule 20) emits only a `Warning` event without affecting `Ready`. None of these constraints are surfaced via admission webhook, because Kaalm has no admission webhook server.

Rule numbers are stable identifiers. Other pages cite them by number, so the numbering below never changes.

![Swimlane flow from Developer through apiserver/CEL, etcd, Reconciler, and status. A kubectl apply first meets the CRD CEL gate, which carries only rules 16, 17, 21, 25, 27, 32, and 34 and rejects violations before the object reaches etcd. Everything that passes is stored, and the reconciler then reads the stored object and applies the reconcile-time gate, which forks into four outcome classes: Ready=False with a per-rule reason for rules 15, 19, 22, 23, 25, 27, 28, 31, and 33; phase=Degraded with preDegradedPhase on an Agent for rules 2, 5, 24, 26, 29, and 30; phase=Failed on an AgentTask for rules 2, 5, and 24, because AgentTask has no Degraded phase; and a Warning event that leaves Ready unaffected for rule 20.](../diagrams/validation-enforcement.svg)

Reading the diagram: the vertical position of the `etcd` lane is the whole point. A CEL rule is rejected to the left of it, so the object never exists and the developer gets the error back on the terminal. Every other rule is enforced to the right of it, on an object that is already stored, which is why those violations can only be reported as status. The four arms out of the reconcile-time gate are the four shapes that report takes, and the legend maps each rule number to its `reason` string.

1. **Class references must resolve.** `Agent.spec.agentClassRef` and `AgentTask.spec.agentClassRef` must resolve to an existing AgentClass.
2. **The workload image must be on the class allowlist.** `Agent.spec.image` and `AgentTask.spec.image` must match at least one pattern in `AgentClass.spec.image.allowedImages` (if the list is non-empty).
3. **Provider references must resolve.** Every `providerRef` in Agent/AgentTask must resolve to a ModelProvider (when `spec.providers` is present).
4. **A provider must admit the workload's namespace.** Every referenced ModelProvider must have the Agent's namespace in its `allowedNamespaces`.
5. **A provider must be on the class allowlist.** Every referenced ModelProvider must appear in the AgentClass's `allowedProviders`.
6. **Resource limits are capped by the class.** Resource `limits` in Agent/AgentTask must not exceed `AgentClass.spec.resources.maxLimits`.
7. **Volume size is capped by the class.** `persistence.sizeGi` must not exceed `AgentClass.spec.persistence.maxSizeGi`.
8. **Idle timeout is capped by the class.** `lifecycle.idleTimeout` must not exceed `AgentClass.spec.lifecycle.maxIdleTimeout`.
9. **Wake timeout is capped by the class.** `lifecycle.wakeTimeout` must not exceed `AgentClass.spec.lifecycle.maxWakeTimeout`.
10. **Hibernation delay is capped by the class.** `lifecycle.hibernationDelay` must not exceed `AgentClass.spec.lifecycle.maxHibernationDelay`.
11. **Fallback chains must terminate.** `ModelProvider.spec.fallback` chains must not be circular. The check walks the full chain up to `maxFallbackDepth`.
12. **Fallback stays within formats the gateway can translate.** *(Restated in v0.7.0; before, same type only.)* Each `ModelProvider.spec.fallback[]` entry must have the same `spec.type` as the provider naming it, or a type the gateway translates to: `anthropic` and `openai` or `openai-compatible` may reference each other in either direction; `google-vertex` may reference only `google-vertex` and be referenced only by it. Checked at reconcile time by the ModelProviderReconciler while walking the chain (with rule 11); the gateway repeats the check per candidate as static eligibility. See [Crossing formats](../gateways/llm/fallback.md#crossing-formats).
13. **Channel targets must resolve.** `AgentChannel.spec.agentRef` must resolve to an existing Agent.
14. **A channel needs a reachable agent Service.** The referenced Agent must have `spec.service.enabled: true` for an AgentChannel to be valid.
15. **A channel's path must live under its own namespace prefix.** The channel's path (`AgentChannel.spec.webhook.path`, or since v0.7.0 `spec.discord.path` or `spec.whatsapp.path`, whichever block the type selects) must begin with `/channels/{namespace}/`, where `{namespace}` matches the AgentChannel's own namespace. Enforced at **reconcile time** by the AgentChannelReconciler (`Ready=False, reason=InvalidPath`) and independently by the gateway, which refuses to register non-conforming paths. CRD CEL cannot express this rule, because `metadata.namespace` is not reachable from CRD validation rules at any scope; only `metadata.name` and `metadata.generateName` are (contrast rule 21, which is expressible because it needs only `metadata.name`). Namespace-scoping eliminates cross-tenant path conflicts at the routing layer: two namespaces cannot claim the same path prefix, and a violating channel never receives traffic. Within a namespace, paths must still be unique. On conflict, the reconciler marks the newer AgentChannel (by `creationTimestamp`) as `Ready=False, reason=PathConflict`, and the gateway routes webhook traffic only to AgentChannels whose `status.conditions[type=Ready].status == True` (see [Request Flow step 4](../gateways/user/overview.md#request-flow)).
16. **A channel's path must not claim the reserved API prefix.** The channel's path (`spec.webhook.path`, `spec.discord.path`, or `spec.whatsapp.path`) must not begin with `/v1/`. This overlaps rule 15 (the required `/channels/` prefix inherently avoids `/v1/`), but rule 15 is reconcile-time while this rule is field-scoped CRD CEL. Retaining it makes it the only **apply-time** guard on reserved paths: a `/v1/`-prefixed path is rejected at the API server before the reconciler ever observes it. See [Reserved Gateway Paths](../gateways/api/overview.md#reserved-gateway-paths).
17. **An exit-code task cannot collect artifacts.** `AgentTask` with `spec.completion.condition: exitCode` must not declare `spec.artifacts`. Artifact collection requires the `POST /v1/task/complete` payload, which is only available in `agentReported` mode. Enforced via CRD schema validation (CEL).
18. **A budget degrade target must name a real model.** `ModelProvider.budget.policies[x].degradeTo` must match a model `id` in the same ModelProvider's `spec.models` list. A missing target model would cause silent routing failures when the budget threshold is crossed.
19. **Egress CIDR entries must be well-formed.** `AgentClass.spec.network.egress.allowedCIDRs` entries must parse as valid CIDR blocks (IPv4 or IPv6). Invalid entries cause `Ready=False, reason=InvalidCIDR` on the AgentClass.
20. **Egress host entries must be valid DNS names, and they only take effect when the CNI can enforce them.** `AgentClass.spec.network.egress.allowedHosts` entries must be valid DNS names (RFC 1123). If the field is non-empty and the AgentClassReconciler's startup CNI probe did not detect FQDN egress policy support (Cilium's `CiliumNetworkPolicy` CRD or Calico Enterprise's equivalent), the reconciler emits a `Warning` event (`reason=FQDNPolicyUnsupported`) on the AgentClass and ignores `allowedHosts` when synthesizing the per-agent NetworkPolicy. The AgentClass still becomes `Ready=True`; `allowedCIDRs` alone governs egress.
21. **Agent and AgentTask names must be plain DNS labels: lowercase alphanumerics and hyphens, no dots, at most 63 characters.** `Agent.metadata.name` and `AgentTask.metadata.name` must match `^[a-z0-9]([-a-z0-9]*[a-z0-9])?$` and satisfy `size(self.metadata.name) <= 63`. Names are used verbatim as single DNS labels in cert SANs and as per-Agent Service names, both of which cap at 63; Kubernetes itself would allow up to 253. Enforced at apply time via **root-scoped** CRD CEL on both kinds (`self.metadata.name.matches(…) && size(self.metadata.name) <= 63`). `metadata.name` and `metadata.generateName` are the only metadata fields reachable from CRD validation rules, and only from the object root; `metadata.namespace` is not, which is why rule 15 is reconcile-time. Kubernetes allows DNS-1123 *subdomain* names (which permit dots) on most namespaced resources. Kaalm restricts Agent and AgentTask to the stricter label form so the gateway's cert-SAN namespace extraction, which reads label index 1 of the `.`-split SAN, cannot be tricked by a dotted name. See the [Agent](agent.md) and [AgentTask](agenttask.md) design notes for the threat scenario and [Namespace Identification § Mode 1](../gateways/llm/workload-identity.md) for the gateway's defense-in-depth label-count check.
22. **Callback URLs must be HTTPS and must not point into internal address space.** `AgentChannel.spec.webhook.callbackUrl`, when set, must use the `https://` scheme, and its host must not resolve to loopback (127.0.0.0/8, ::1), link-local (169.254.0.0/16, fe80::/10), RFC1918 private ranges (10/8, 172.16/12, 192.168/16), unique-local IPv6 (fc00::/7), shared address space (100.64.0.0/10, RFC 6598, used as the Pod or Service CIDR by several managed clusters), benchmarking space (198.18.0.0/15, RFC 2544), or the cloud-metadata IPs 169.254.169.254 / fd00:ec2::254. Violations set `Ready=False, reason=InvalidCallbackUrl`. The AgentChannelReconciler performs the check at admission/reconcile time. The gateway re-resolves the host and repeats the check on every delivery attempt to prevent DNS rebinding; see [Request Flow](../gateways/user/overview.md#request-flow). The deny-internal default may be opened for specific targets with the Helm value `gateway.callbackUrl.allowlist` (DNS-name suffixes and CIDR blocks), which both this check and the gateway share. Loopback, link-local and the cloud-metadata IPs are refused even when listed, so an allowlist can reach in-cluster receivers but cannot re-expose the SSRF-critical targets.
23. **Image pull Secrets named by the class must exist where the workload runs.** `AgentClass.spec.image.imagePullSecrets[*].name`, when referenced by an Agent or AgentTask, must exist as a Secret in the **referencing workload's namespace** at reconcile time. AgentClass is cluster-scoped but Secrets are namespace-scoped, and the controller does not copy Secrets across namespaces. Missing Secrets set `Ready=False, reason=ImagePullSecretMissing` on the Agent/AgentTask with a message naming the namespace and secret, and the Pod is not created. Checked in AgentReconciler and AgentTaskReconciler; see the [AgentClass design notes](agentclass.md#design-notes).
24. **A workload cannot enable persistence that its class forbids.** `Agent.spec.persistence.enabled` and `AgentTask.spec.persistence.enabled` must not be `true` if the referenced AgentClass has `spec.persistence.enabled: false`. The class is the authority on whether persistence is allowed for workloads of that category; a developer cannot opt in to a PVC that the class disallows. Violations follow the established AgentClass-vs-spec mismatch handling (see [AgentClass change handling](../controller/change-propagation.md#agentclass-change-handling)):
    - **Agent**: transitions to `phase=Degraded, reason=PersistenceNotAllowed` with `preDegradedPhase` set. The Pod and PVC are not created (or not recreated, if class drift introduced the conflict after the Pod was already running). The Agent re-enters its prior phase when the developer aligns the spec.
    - **AgentTask**: transitions to `phase=Failed, reason=PersistenceNotAllowed`. AgentTask has no `Degraded` phase; this matches the AgentClass-drift handling for backoff retries documented in [AgentTaskReconciler](../controller/reconcilers.md#agenttaskreconciler).

    Enforced at reconcile time by AgentReconciler and AgentTaskReconciler. CRD CEL cannot express this rule because it spans two resources and Kubernetes CEL validations on Agent cannot read AgentClass fields.
25. **A callback URL without callback auth is invalid.** When `AgentChannel.spec.webhook.callbackUrl` is set, `AgentChannel.spec.webhook.callbackAuth` must also be set. Enforced at apply time via CRD CEL on AgentChannel (`has(self.spec.webhook.callbackUrl) ? has(self.spec.webhook.callbackAuth) : true`). Outbound callbacks must be cryptographically attributable to the gateway so receivers can reject forged POSTs; an unsigned `callbackUrl` would let any third party that learns the URL deliver fake response or error payloads. The AgentChannelReconciler additionally validates that the referenced Secret exists and contains the configured `data` key, the same shape as the inbound `auth` validation. Violations set `Ready=False, reason=CallbackAuthMissing` (CEL bypass case) or `reason=CallbackAuthInvalid` (Secret not found / key missing). See [Callback delivery](../gateways/api/async-responses.md) for the wire contract and the [threat model](../security/threat-model.md) for the forgery row.
26. **An Agent cannot enable hibernation that its class forbids.** `Agent.spec.lifecycle.hibernationEnabled` must not be `true` if the referenced AgentClass has `spec.lifecycle.hibernationAllowed: false`. The class is the authority on whether hibernation is allowed for workloads of that category; a developer cannot opt in to hibernation that the class disallows. Violations follow the same AgentClass-vs-spec mismatch handling as rule 24: the Agent transitions to `phase=Degraded, reason=HibernationNotAllowed` with `preDegradedPhase` set, and the Pod is not created (or not recreated, if class drift introduced the conflict after the Pod was already running). The Agent re-enters its prior phase when the developer aligns the spec. AgentTask is not affected, because hibernation does not apply to one-shot tasks. Enforced at reconcile time by AgentReconciler. CRD CEL cannot express this rule because it spans two resources, the same reasoning as rule 24.
27. **A pre-existing claim excludes a provisioning size, and the claim must exist.** `Agent.spec.persistence.existingClaim`, when set, must (a) not be combined with `persistence.sizeGi`, enforced at apply time via CRD CEL on the `persistence` block (`!has(self.sizeGi) || !has(self.existingClaim)`), and (b) name a PersistentVolumeClaim that exists in the Agent's namespace at reconcile time. A missing claim sets `Ready=False, reason=ExistingClaimNotFound` with a message naming the claim, and the Pod is not created. Rule 24 (class-level `persistence.enabled`) applies to `persistence.enabled: true` regardless of whether the PVC is Kaalm-provisioned or pre-existing. The reconciler adds no ownerRef to a pre-existing PVC, so `pvcRetention` semantics apply only to Kaalm-provisioned PVCs; see the [Agent design notes](agent.md). AgentTask does not support `existingClaim` (the field exists only on the Agent schema).
28. **Workloads are forbidden in the system namespace.** `Agent`, `AgentTask`, and `AgentChannel` resources must not be created in `kaalm-system`. The reconcilers refuse to provision workloads there: `Ready=False, reason=SystemNamespaceForbidden`, no child resources created. This is a SAN-integrity guard. Per-Agent certificates carry the SAN `{name}.{namespace}.svc.cluster.local`, so an Agent named `kaalm-gateway` in `kaalm-system` would be issued a certificate whose SAN equals the gateway's own, the exact identity that every internal SAN-based authorization (activator, `/v1/activity`, `/v1/channels/health`, and the agent-side `/v1/message` client-cert check) trusts. Enforced at reconcile time, because namespace scoping is not expressible in CRD CEL (the same limitation as rule 15). See the [threat model](../security/threat-model.md) for the collision scenario.
29. **Hibernation requires persistence on the same Agent.** `Agent.spec.lifecycle.hibernationEnabled` must not be `true` unless the same Agent has `spec.persistence.enabled: true`. Hibernation works by deleting the Pod while keeping the PVC and recreating the Pod with the same mount ([Hibernation mechanics](../controller/hibernation-and-wake.md#hibernation-mechanics)), and [The Runtime Contract](../runtime/contract.md) item 7 requires hibernation-enabled agents to persist their message-dedup buffer across Pod restarts. Neither is possible without a PVC. Violations follow the same handling as rules 24 and 26: the Agent transitions to `phase=Degraded, reason=HibernationRequiresPersistence` with `preDegradedPhase` set, and the Pod is not created (or not recreated). The Agent re-enters its prior phase when the developer aligns the spec. AgentTask is not affected, because hibernation does not apply to one-shot tasks. Enforced at reconcile time by AgentReconciler alongside rules 24 and 26; the three checks share the mismatch-handling path, and reconcile-time enforcement surfaces the violation on pre-existing Agents as recoverable `Degraded` status rather than stranding them behind a new apply-time rule.
30. **An Agent cannot mount a handler that its class forbids.** `Agent.spec.handler` must not be set unless the referenced AgentClass has `spec.image.allowHandlerMounts: true` (default `false`). Rule 2 makes `allowedImages` an image review boundary; a mounted handler ([Reference Base Images](../runtime/base-images.md)) injects new code into an image that review already approved, so the class is the authority on whether ConfigMap-sourced code is acceptable for workloads of its category. Violations follow the AgentClass-vs-spec mismatch handling of rules 24, 26, and 29: the Agent transitions to `phase=Degraded, reason=HandlerMountNotAllowed` with `preDegradedPhase` set, and the Pod is not created (or not recreated, if class drift introduced the conflict, including a platform team flipping `allowHandlerMounts` to `false` on a live class). The Agent re-enters its prior phase when the specs align. AgentTask is not affected: the `handler` field exists only on the Agent schema (see [Task mode](../runtime/base-images.md#task-mode)). Enforced at reconcile time by AgentReconciler; CRD CEL cannot express this rule because it spans two resources, the same reasoning as rule 24.
31. **The handler ConfigMap must exist where the Agent runs.** `Agent.spec.handler.configMapRef.name`, when set, must name a ConfigMap that exists in the Agent's namespace at reconcile time. A missing ConfigMap sets `Ready=False, reason=HandlerConfigMapNotFound` with a message naming the namespace and ConfigMap, and the Pod is not created, the same pre-Pod surfacing as rules 23 and 27: a clear condition rather than a Pod wedged in `ContainerCreating` on a missing volume source. The reconciler adds **no ownerRef** to the ConfigMap: it is developer-owned, survives Agent deletion, and its content is not tracked (handler updates land on the next Pod creation; see [Handler update semantics](../runtime/base-images.md#handler-update-semantics)). Checked in AgentReconciler alongside rule 23.
32. **Hard budget enforcement requires a block policy.** `ModelProvider.spec.budget.enforcement: hard` requires at least one `policies[]` entry with `action: block`. Hard mode's entire effect is to turn block thresholds into a guaranteed cap ([Hard Enforcement](../gateways/llm/budgets-and-rate-limits.md#hard-enforcement)); with no block policy there is no ceiling to defend and the mode would be a silent no-op. Enforced at apply time via CRD CEL on the budget block (`self.enforcement != 'hard' || self.policies.exists(p, p.action == 'block')`).
33. **Hard budget enforcement requires a fully priced catalog.** When `budget.enforcement: hard`, every model in `spec.models` must carry `costPer1MInputTokens` and `costPer1MOutputTokens` values the gateway's ledger can parse. An unpriced model's calls cost zero in the ledger, so a cap over them is never reached and the observed-traffic margin never widens: hard enforcement over an unpriced catalog would be silently vacuous. Enforced at reconcile time by the ModelProviderReconciler alongside rule 18 (`Ready=False, reason=HardBudgetUnpriced`, message naming the unpriced models), because pricing validity must match the ledger's decimal parser exactly, which CRD CEL cannot replicate.
34. **The boundary margin must sit strictly below every block threshold.** `budget.hard.boundaryMarginPercent` must be at least 0 (field-level bound) and, for every `policies[]` entry with `action: block`, strictly less than that policy's `atPercent`; a margin at or above a block threshold would put the boundary region's start at or below zero utilization and serialize all traffic from the first request. Enforced at apply time via CRD CEL on the budget block (`!has(self.hard) || self.policies.all(p, p.action != 'block' || self.hard.boundaryMarginPercent < p.atPercent)`). The configured margin is a floor for the effective margin; the runtime widening is [Hard Enforcement](../gateways/llm/budgets-and-rate-limits.md#hard-enforcement)'s job.
35. **Tool references must resolve.** *(Since v0.4.0; designed with the [tool plane](../gateways/tool-plane.md).)* Every workload's `spec.tools[].providerRef` must resolve to an existing ToolProvider, the rule 3 analog for the tool grant chain. Applies to Agent and AgentTask alike.
36. **A ToolProvider must admit the workload's namespace.** *(Since v0.4.0; designed with the tool plane.)* Every referenced ToolProvider must have the workload's namespace in its `allowedNamespaces`, the rule 4 analog. Together with rule 37 this follows the class-mismatch handling of rules 2 through 5: recoverable `Degraded` for an Agent, terminal `Failed` for an AgentTask, never a stranded workload.
37. **A ToolProvider must be on the class allowlist.** *(Since v0.4.0; designed with the tool plane.)* Every referenced ToolProvider must appear in the AgentClass's `allowedToolProviders`, the rule 5 analog. The class remains the authority on which capabilities workloads of its category may reach.
38. **Granted tools must exist in a declared catalog.** *(Since v0.4.0; designed with the tool plane.)* When a ToolProvider declares a `tools` catalog, every tool name in a workload's grant must appear in it. A violation follows the same recoverable class-mismatch handling with its own `reason=ToolNotInCatalog`, naming the missing tools; when no catalog is declared, the server's own `tools/list` governs and this rule does not apply.
39. **A channel's type and its configuration block must match.** *(Since v0.7.0; designed with the [platform adapters](agentchannel.md#platform-types).)* `AgentChannel.spec.type` selects exactly one of `spec.webhook`, `spec.discord`, and `spec.whatsapp`, and that block must be set while the other two are absent. Enforced at apply time via CRD CEL on the spec (`(self.type == 'webhook') == has(self.webhook) && (self.type == 'discord') == has(self.discord) && (self.type == 'whatsapp') == has(self.whatsapp)`), so a channel that names one platform and configures another never reaches the reconciler. The adapter is chosen by `type`; the block is what the adapter reads.
40. **Platform credentials must resolve with the keys the type requires.** *(Since v0.7.0; designed with the platform adapters.)* `spec.discord.credentialsRef` and `spec.whatsapp.credentialsRef` must name a Secret in the AgentChannel's namespace that carries the type's required keys: `publicKey` for Discord (`botToken` is optional), and `verifyToken`, `appSecret`, and `accessToken` for WhatsApp. A missing Secret or key sets `Ready=False, reason=CredentialsMissing`, the same signal as a missing webhook auth Secret; a Discord `publicKey` that is not 32 bytes of hex sets `Ready=False, reason=CredentialsInvalid`, because the verifier cannot be built from it and every inbound request would fail with a misleading `401`. Enforced at reconcile time by the AgentChannelReconciler after the per-channel credential Role is scoped to the Secret, the same order as the webhook auth check; see [AgentChannelReconciler](../controller/reconcilers.md#agentchannelreconciler).
41. **A model map must name real models on both ends.** *(Since v0.7.0; designed with [cross-format fallback](../gateways/llm/fallback.md#crossing-formats).)* In `ModelProvider.spec.fallback[].modelMap`, every key must match a model `id` in this provider's `spec.models` and every value a model `id` in the referenced provider's `spec.models`. A violation sets `Ready=False, reason=InvalidModelMap` on the provider carrying the map, naming the entry; a map on an edge that does not cross formats is allowed and applied the same way. Enforced at reconcile time by the ModelProviderReconciler alongside rules 11 and 12, because it follows the reference; the gateway then trusts the map and tests only the mapped model's presence (check 3).

Field-level schema validation uses CEL expressions (`x-kubernetes-validations`) embedded in the CRD OpenAPI schema. No admission webhook server is required.

### Enforcement points

Many rules above state their enforcement point inline. The rest follow from one principle: a check that compares fields across two resources (a workload against its AgentClass or ModelProvider) cannot run in CRD CEL, because CEL on one object cannot read another, so it runs at reconcile time. The remaining rules resolve as follows.

**Provider access (rules 3, 4, 5).** A referenced ModelProvider that does not resolve, does not admit the workload's namespace, or is not on the class allowlist is a cross-resource check. All three run at reconcile time and share one outcome: `phase=Degraded, reason=ClassConstraintViolation` on an Agent, `phase=Failed` on an AgentTask. A ModelProvider or AgentClass change can newly trigger any of them (see [Change Propagation](../controller/change-propagation.md#agentclass-change-handling)).

**Class caps (rules 6, 7, 8, 9, 10).** Resource limits, volume size, and the three lifecycle timeouts are not rejected when they exceed the class maximum. They are **clamped**: the effective value is the smaller of the requested value and the class cap, computed at reconcile time. Clamping is what lets an AgentClass tighten a cap without degrading every workload that asked for more (see the resources.limits clamp in [Change Propagation](../controller/change-propagation.md#agentclass-change-handling)).

**Other reconcile-time rejects.** These set `Ready=False` at reconcile time: rule 1 (an unresolvable `agentClassRef`), rules 11 and 12 (fallback chains, checked by walking the referenced ModelProviders), rule 13 (an unresolvable channel `agentRef`), rule 14 (a target Agent with `service.enabled: false`, `reason=AgentServiceDisabled`), rule 18 (a `degradeTo` naming no real model, `reason=InvalidDegradeTarget`), rule 33 (hard budget enforcement over an unpriced catalog, `reason=HardBudgetUnpriced`), rule 40 (platform credentials missing or malformed, `reason=CredentialsMissing` or `CredentialsInvalid`), and rule 41 (a model map naming a model that does not exist, `reason=InvalidModelMap`). Rules 11, 12, 18, 33, and 41 concern a single ModelProvider but still run at reconcile time: 11, 12, and 41 must follow references to other providers, while 18 and 33 are enforced by the ModelProviderReconciler alongside the cost-sanity check because their checks must match the gateway's model lookup and price parsing exactly (see [ModelProviderReconciler](../controller/reconcilers.md#modelproviderreconciler)).

## Defaulting

AgentClass defaults are applied at reconcile time when Agent/AgentTask fields are absent:

| Workload field | Defaults from |
|---|---|
| `resources` | `AgentClass.spec.resources.defaults` |
| `persistence.sizeGi` | `AgentClass.spec.persistence.defaultSizeGi` (see note below) |
| `image` | `AgentClass.spec.image.defaultImage` |
| `lifecycle.idleTimeout` | `AgentClass.spec.lifecycle.defaultIdleTimeout` |
| `lifecycle.hibernationDelay` | `AgentClass.spec.lifecycle.defaultHibernationDelay` |
| `lifecycle.wakeTimeout` | `AgentClass.spec.lifecycle.defaultWakeTimeout` |

The `persistence.sizeGi` default is not applied when `persistence.existingClaim` is set: no PVC is provisioned in that case, so a size is meaningless (see rule 27).

Defaults are applied at reconcile time rather than admission. The stored spec reflects what the developer wrote. Effective values can be derived by merging the AgentClass defaults at read time. This avoids a mutating webhook dependency while keeping the behavior predictable.
